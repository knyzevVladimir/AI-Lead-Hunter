# Переработка фронтенда AI Lead Hunter

Статус на 29 июля 2026. Ветка `feat/frontend-redesign`.

Документ описывает, что уже сделано, что осталось, и какие решения приняты —
чтобы работу можно было продолжить без восстановления контекста.

> **Важно:** ветка находится в промежуточном состоянии. Старый фронтенд удалён,
> новый собран до уровня фундамента: конфигурация, дизайн-система и слой данных
> готовы, экранов ещё нет. `src/app/page.tsx` — временная заглушка для проверки
> сборки. В `main` вливать нельзя.

---

## 1. Что это за переработка

Полная замена фронтенда. Бэкенд не тронут ни одной строкой — новый интерфейс
строится строго на существующем контракте API, который предварительно был
вычитан из исходников бэкенда и зафиксирован в
[`docs/API-CONTRACT.md`](./API-CONTRACT.md).

### Продуктовая идея

Вместо набора несвязанных страниц — единый рабочий кабинет, в котором AI не
отдельный раздел, а слой поверх всего интерфейса.

Ключевые решения:

1. **AI доступен с любого экрана.** Copilot живёт в правом доке и видит контекст:
   активные фильтры, выделенные лиды, открытую компанию. Поверх чата — реестр
   действий, поэтому AI выполняет реальные операции в интерфейсе, а не только
   отвечает текстом.
2. **Один рабочий экран вместо трёх.** Таблица и карта — два представления
   одного набора данных с общим выделением, переключение не теряет выбор.
3. **Карта на MapLibre GL вместо Leaflet.** Векторные тайлы, кластеризация,
   выделение множества компаний лассо. На растровом Leaflet этого класса
   взаимодействия не получить.
4. **Состояние в URL.** Фильтры, сортировка, выбранный лид, режим просмотра —
   любой экран можно расшарить ссылкой.
5. **Ядро отделено от React.** `src/core/` не импортирует React, чтобы будущий
   Telegram-бот и Mini App переиспользовали ту же логику.

### Планируемая навигация

| Маршрут | Экран | Роль |
|---|---|---|
| `/` | Command Center | AI-запрос в центре, метрики, быстрые сценарии, горячие лиды |
| `/hunt` | Поиск | композер запроса, стадии прогресса, живая лента находок |
| `/leads` | Лиды | главный экран: таблица ⟷ карта, фасеты, массовые действия, детали |
| `/map` | Карта | полноэкранный режим, кластеры, выделение лассо |
| `/pipeline` | Воронка | канбан по восьми статусам, drag-n-drop |
| `/outreach` | Рассылки | кампании и визард: лиды → услуга → AI-превью → запуск |
| `/inbox` | Диалоги | переписка с клиентами, задел под авто-ответы AI |
| `/settings` | Настройки | интеграции, провайдеры, тема, параметры AI |

## 2. Сделано

### Стек и конфигурация

Полностью новый проект вместо прежнего Next 14 / React 18 / Tailwind 3.

| Что | Версия | Зачем |
|---|---|---|
| Next.js | 16.2 | App Router, серверные компоненты |
| React | 19.2 | — |
| TypeScript | 5.9, strict | — |
| Tailwind CSS | 4.3 | токены дизайн-системы декларативно, через `@theme` |
| Motion | 12 | анимации, shared layout |
| TanStack Query | 5 | серверное состояние, кэш, оптимистичные обновления |
| TanStack Table + Virtual | 8 / 3 | виртуализированная таблица на 10k+ строк |
| MapLibre GL | 6 | карта |
| Radix UI | — | доступные примитивы (диалоги, поповеры, табы и прочее) |
| Zustand | 5 | состояние интерфейса |
| nuqs | 2 | синхронизация фильтров с URL |
| cmdk | 1 | командное меню |
| sonner | 2 | уведомления |
| Recharts | 3 | графики |
| dnd-kit | 6 | drag-n-drop канбана |
| ogl, gsap | — | зависимости готовых компонентов |

Файлы: `package.json`, `tsconfig.json`, `next.config.mjs`,
`postcss.config.mjs`, `Dockerfile`, `.dockerignore`, `.env.local.example`.

Сборка проверена: `next build` проходит, TypeScript ошибок не даёт.

**Прокси до бэкенда.** По умолчанию фронтенд обращается к same-origin
`/api/backend/*`, который Next перенаправляет на бэкенд. Это снимает вопрос CORS
в любом окружении. Прямое обращение включается через `NEXT_PUBLIC_API_URL`.

### Дизайн-система

`src/app/globals.css` — единый источник визуальных решений.

- **Палитра в OKLCH**, две темы из одного набора решений. Тёмная тема основная:
  графит с холодным подтоном, ориентир — Linear, Vercel, Cursor, Raycast.
  Светлая тема полноценная, не побочная — фон намеренно не чисто белый.
- **Токены поверхностей** (`bg`, `surface`, `surface-2`, `surface-3`,
  `surface-inset`), границ, текста четырёх уровней контраста.
- **Два акцента.** Основной — фиолетовый, для действий интерфейса. Отдельный
  голубой — для AI-моментов: подсказок, генерации, объяснений. Без этого
  разделения перестаёт читаться, где кнопка, а где ответ модели.
- **Шкала температуры лида** от холодного к горячему. Красный намеренно не
  используется: отсутствие сайта — это возможность, а не ошибка, и палитра не
  должна читаться как предупреждение.
- **Тени** построены на цветовом тоне фона, а не на нейтрально-сером — серая
  тень на цветном графите выглядит грязно.
- **Кривые анимации** и набор keyframes, единые для всего интерфейса.
- **Базовый слой:** типографика с плотным трекингом на крупных кеглях,
  табличные цифры, единое кольцо фокуса только для `focus-visible`,
  оформленные скроллбары, полное снятие движения при `prefers-reduced-motion`.
- **Утилиты повторяющихся паттернов:** стеклянные поверхности, световая кромка
  панели, сетка-подложка, маски затухания к краям.
- **Интеграция MapLibre с темой** — контролы карты приведены к дизайн-системе.

Шрифты: Inter и JetBrains Mono через `next/font`, с кириллическим сабсетом.

### Слой данных и ядро

`src/core/` — без React-зависимостей, пригоден для Telegram-бота.

- **`enums.ts`** — перечисления бэкенда плюс всё их представление в интерфейсе:
  русские подписи, семантический тон, подсказки, порядок вывода. Восемь статусов
  воронки, источники данных с признаком «работает без ключа», состояния сайта,
  каналы с признаком «отправка реально реализована», типы услуг, подписи
  технических проверок сайта, шкала температуры лида, цели экспорта, тоны оффера.
  Подпись статуса нигде не пишется вручную второй раз.
- **`types.ts`** — типы сущностей, один в один по контракту API.
- **`api.ts`** — типизированный клиент на все 19 эндпоинтов. Каждый метод
  принимает `AbortSignal`, потому что поиск и анализ на бэкенде синхронные и
  отмена на клиенте — единственный способ прервать ожидание. Класс `ApiError`
  разбирает ошибки валидации Pydantic и отдаёт человеческое сообщение под каждый
  код ответа. Отмена отделена от ошибки.
- **`format.ts`** — форматирование: числа, компактные метрики, проценты,
  **русская плюрализация**, относительное время, длительность, домен без схемы,
  телефон, инициалы компании, устойчивый хеш для цвета аватара, сборка строки
  адреса без дублирования города.
- **`lib/utils.ts`** — слияние классов, а также `runPool`: выполнение задач с
  ограниченной параллельностью. Массовых операций на бэкенде нет, поэтому
  «сменить статус у 200 лидов» превращается в 200 запросов, и без ограничения
  это положит и браузер, и сервер.

### Подготовка компонентов

Из приложенного `1.txt` извлечены и нормализованы исходники пяти компонентов
(файл был продублирован пустыми строками — восстановлен): `Ferrofluid`,
`SpecularButton`, `CurvedInput`, `AnimatedList`, `MagicBento`.

Сложены в `frontend/vendor-source/` вне сборки, с описанием того, что нужно
изменить при переносе. См. `frontend/vendor-source/README.md`.

**Остальных ~25 компонентов из перечня в репозитории нет** — ни в старом
фронтенде, ни в `1.txt`. Нужные из них написаны не будут «как есть», а
реализуются в стиле дизайн-системы.

### Документация

`docs/API-CONTRACT.md` — полный контракт бэкенда, вычитанный из исходников:
все эндпоинты с параметрами и ответами, перечисления с точными строковыми
значениями, формы сущностей, возможности разбора запросов в чате, модель
асинхронности, состояние диалогов, пробелы API, состояние авторизации.

## 4. Ограничения бэкенда, которые определили архитектуру

Четыре места, где бэкенд не даёт того, что нужно интерфейсу такого класса.
Правок бэкенда ни одно не требует, но важно понимать, где интерфейс работает
«в долг».

### Поиск синхронный, задач и статусов задач нет

`POST /api/search` парсит внутри запроса и может идти десятки секунд. Нет
идентификатора задачи, нет опроса состояния, нет websocket.

**Решение:** осмысленные стадии прогресса на клиенте, таймер, отмена через
`AbortController`, уведомление о результате. Место под реальный опрос состояния
изолировано в одном хуке — подключится заменой.

### AI-чат — это regex-парсер, не языковая модель

`POST /api/chat` понимает фиксированный список категорий и городов, отдаёт один
JSON без стриминга и умеет только фильтровать уже загруженные компании. Ни
поиск, ни рассылку, ни смену статуса он запустить не может.

**Решение:** Copilot строится как клиентский исполнитель действий. Распознавание
фильтров отдаём бэкенду, а поверх — свой реестр инструментов, которые делают
реальную работу в приложении. Пользователь получает «AI делает почти всё
естественным языком» уже сейчас; когда на бэкенде появится модель со
стримингом, меняется только транспорт.

### Диалогов с клиентами в бэкенде нет вообще

Входящие ответы негде хранить: `Message.reply_at` никто не заполняет, webhook
приёма писем отсутствует, статус `replied` никто не выставляет — поэтому
счётчик ответов на дашборде всегда ноль.

**Решение:** Inbox строится на реальных исходящих сообщениях, сгруппированных в
треды по компании, с честным пустым состоянием для входящих и изолированным
адаптером. Архитектура сразу учитывает авто-ответы AI: у треда есть режим
(ручной, AI-подсказка, AI-автоответ) и точка передачи лида человеку.

### Нет массовых операций, авторизации и сохранённых представлений

Смена статуса — только по одному лиду, удаления нет, пользователей и тенантов нет.

**Решение:** массовые действия — управляемая очередь параллельных запросов
(`runPool`) с прогрессом и откатом при ошибке. Сохранённые представления — через
URL и локальное хранилище. Авторизация не имитируется: это отдельная задача
бэкенда.

## 5. Как запустить

```bash
cd frontend
npm ci
cp .env.local.example .env.local
npm run dev
```

Проверки:

```bash
npm run typecheck   # tsc --noEmit
npm run build       # next build
```

Бэкенд поднимается как раньше — `docker-compose up`. Когда демо-режим будет
готов, интерфейс можно будет смотреть и без него, выставив
`NEXT_PUBLIC_DEMO=1`.
