# AI Lead Hunter — Backend HTTP API Contract

Generated by reading the backend source directly (not the OpenAPI schema at runtime). Treat this as ground truth for a frontend rewrite: **do not change any backend field name, route, or status code** — the frontend must conform to this contract, not the other way around.

- **Base prefix**: all API routes are mounted under `/api` (`settings.API_PREFIX`, `app/main.py:33`). Two extra routes exist outside the prefix: `GET /health` and `GET /`.
- **Docs**: Swagger UI at `/docs` (FastAPI default, title "AI Lead Hunter", version `1.0.0`).
- **CORS**: `CORSMiddleware` allows origins from `settings.CORS_ORIGINS` (default `["http://localhost:3000", "http://127.0.0.1:3000"]`), `allow_credentials=True`, all methods, all headers. Configurable via env var `CORS_ORIGINS`.
- **Content type**: all bodies are JSON except `GET /api/export/csv` (`text/csv` streaming download).
- **Errors**: FastAPI/Pydantic validation errors → `422` with the standard `{"detail": [...]}` shape. Explicit app errors use `HTTPException(status_code, "message")` → `{"detail": "message"}`. Notable codes: `404` (not found), `422` (validation / provider not configured / missing required field like company email), `502` (upstream provider error, e.g. search or email send failure).
- **Auth**: **none**. See section 8.

## 2. Enums (exact string values) — `backend/app/models/enums.py`

### `Source` (search provider)
```
google_maps | yandex_maps | 2gis | openstreetmap | bing_maps | manual
```
Note: Python member name for `twogis` serializes to string `"2gis"`; member name for `osm` serializes to `"openstreetmap"`. Only `openstreetmap` and `yandex_maps` are guaranteed to work with zero configuration; `google_maps`/`2gis` need `GOOGLE_MAPS_API_KEY`/`TWOGIS_API_KEY`. `bing_maps`/`manual` accepted by the enum/schema but have **no registered parser** (`registry.get_parser` silently falls back to the OSM parser for any unrecognized source).

### `WebsiteStatus`
```
ok | none | broken | unreachable
```
- `ok` = site exists and reachable
- `none` = no website at all
- `broken` = site exists but returns HTTP error status
- `unreachable` = timeout / DNS / connection failure

### `CRMStatus` (lead pipeline status)
```
new | analyzed | email_sent | replied | negotiation | client | rejected | blacklist
```
This is also the exact ordered list of Kanban columns from `GET /api/crm/board`.

### `Channel` (outreach channel)
```
email | telegram | whatsapp | sms | linkedin
```
Only `email` is actually implemented for sending (`POST /api/integrations/send`); other channels can be used for offer generation / message drafting but have no send integration.

### `MessageStatus`
```
draft | queued | sent | replied | failed
```
Note: `Message.status` and `Campaign.status` are stored as untyped `str` columns in the DB/schema (no DB-level enum constraint) — values above are what application code writes, but nothing prevents other strings.

### `ServiceType` (recommended service categories, used in `possible_services`)
```
website | redesign | seo | ads | crm | chatbot | automation | online_booking | whatsapp | ai_assistant | analytics
```

## 4. Chat / NLU Capability — `backend/app/services/aichat/nlu.py`

`parse_query(message: str) -> dict` is a **pure rule-based regex/keyword parser** (Russian-first, some English support). No LLM is used for chat filter parsing (LLM is only used, optionally, for offer generation text). It is deterministic and stateless — no conversation memory across requests.

**Returned filter dict shape** (this is exactly what comes back as `ChatResponse.parsed_filters`):
```json
{
  "category": "стоматология" | null,
  "city": "Москва" | null,
  "no_website": false,
  "has_email": false,
  "no_https": false,
  "no_socials": false,
  "low_rating": false,
  "few_reviews": false,
  "no_booking": false,
  "sort_by_score": false
}
```

**What it can detect:**
- **Category**: first matching key found from `CATEGORY_MAP` in `services/parser/osm.py` (substring match on the lowercased message). Known keys: `барбершоп/barbershop, парикмахерская, салон красоты/beauty, стоматология/dentist, клиника/clinic, кафе/cafe, ресторан/restaurant, фитнес/gym, автосервис/car repair, юрист/lawyer, отель/hotel, магазин/shop`. Anything outside this list is **not recognized as a category** (silently ignored, `category` stays `null` — no fuzzy fallback in chat, unlike raw `/search` which does fuzzy name matching).
- **City**: matched by *stem* substring against a small hardcoded dict (`CITY_STEMS`): `Москва, Санкт-Петербург (also "спб"), Прага, Берлин, Лондон, Париж, Киев, Казань, Новосибирск, Екатеринбург`. Any other city name is not recognized.
- **Boolean flags** via regex, RU+EN: no-website, has-email, no-HTTPS, no-socials, low-rating (<4), few-reviews (<30), no-online-booking, sort-by-score/"perspective".

**What it does NOT do:**
- Cannot understand `radius_km`, `country`, `region`, `min_score` (numeric threshold beyond the hardcoded <4/<30), `monitored`, arbitrary CRM `status` targeting, or any campaign/offer/CRM-mutation intent.
- **Cannot trigger a search** — chat only *filters already-ingested* `Company` rows in the DB (same underlying query shape as `GET /api/leads`, plus the two JSON post-filters `no_https`/`no_booking`/`no_socials`). If nothing has been searched/ingested yet, chat returns `total: 0` and the reply text says so.
- **Cannot trigger a campaign, change a CRM status, send anything, or export** — it is strictly read/filter-only.
- Response is a **single synchronous JSON blob** — no streaming/SSE/websocket, no multi-turn state, no function-calling/tool-use loop server-side.

## 5. Async / Job Model

**There is no background job, task-status, or polling API reachable from HTTP.** Every "action" endpoint (`search`, `analyze`, `analyze-batch`, `offer`, `send`, `export`) executes fully **synchronously within the request/response cycle** and returns the final result directly:

- `POST /api/search` → runs the parser inline, awaits ingestion, then returns.
- `POST /api/leads/{id}/analyze` → runs website fetch + scoring inline, then returns.
- `POST /api/leads/analyze-batch` → **loops** `analyze_company()` for up to 300 companies inline in a single request (docstring literally says "runs inline; use Celery in production" — this is an acknowledged simplification, and a real risk of request timeouts on large batches).
- `POST /api/integrations/send` → calls the email provider's HTTP API/SMTP inline.
- `POST /api/integrations/export` → pushes each lead to the external CRM inline, one HTTP call per lead.

A Celery app **does exist** (`backend/app/workers/celery_app.py`, tasks in `backend/app/workers/tasks.py`: `search_task`, `analyze_company_task`, `analyze_batch_task`, `monitor_companies`, `generate_followups`), but **no HTTP route calls `.delay()` or `.apply_async()` on any of them** — confirmed by grep across `app/api/`. Celery is used exclusively for the **beat schedule** (periodic background jobs: `monitor_companies`, `generate_followups`), which run independently of any user-facing HTTP flow and have no HTTP-visible status/results endpoint either.

**Practical implication for a frontend rewrite**: there is no task id, no `GET /api/tasks/{id}` or `/jobs/{id}` status endpoint, no websocket, no SSE. A "search in progress" or "analyzing…" UI state must be modeled purely as "this fetch() call is pending" — there is nothing to poll. If the rewrite wants a job-queue UX (e.g., "search running in background, notify when done"), that is new backend work, not something to wire up against existing infrastructure.

## 6. Dialogs / Replies Model

**There is no inbound-reply or conversation-thread storage today.** Specifics:

- `Message` (`backend/app/models/campaign.py`) is **outbound-only**: it has `sent_at` and `reply_at` columns, and a `status` that can be set to `"replied"`, but **nothing in the codebase ever sets `reply_at` or transitions a message to `"replied"`** — there is no inbound email/webhook handler, no IMAP polling, no reply-parsing logic anywhere in `backend/app/`. `reply_at` is dead schema (defined, never written).
- `DashboardStats.replies` counts `Message WHERE status='replied'`, but since nothing ever writes that status, this will always be `0` in the current system — it's a metric with no producer.
- `CRMStatus.replied` exists as a manually-settable pipeline stage (via `PATCH /api/crm/{id}/status`), but that's a human clicking a status change in the CRM board — not a system-detected reply.
- There is **no message-thread/dialog view** endpoint — `GET /api/campaigns/messages?company_id=` returns a flat list of all generated/sent `Message` rows for a company (drafts + sent + any future follow-ups), which is the closest thing to a "dialog", but it is one-directional (agency → lead) with no inbound counterpart, no read/unread state, and no in-app rendering of an actual conversation.

**What a "Dialogs" UI would need that doesn't exist:**
1. An inbound message model (sender, received_at, body, channel, linked `company_id`/`message_id` for threading).
2. A webhook/ingestion endpoint (e.g., email reply webhook, WhatsApp/Telegram webhook) to populate it.
3. A `GET /api/dialogs` or `GET /api/companies/{id}/dialog` endpoint returning a merged, chronologically-ordered thread of outbound `Message` + inbound replies.
4. Read/unread or "needs response" flags.
5. A way to actually reply from the UI that maps to `POST /api/integrations/send` today (which works for outbound-only, template/company-linked sends) but has no "reply to this specific inbound message" semantics.

## 7. Gaps — endpoints/capabilities a modern UI would want but do NOT exist

| Desired capability | Current state |
|---|---|
| Job/task status polling (search, batch-analyze, batch-export) | Not present — all synchronous. No task id returned anywhere. |
| WebSocket / SSE for live progress or streaming chat | Not present anywhere in the codebase. |
| Streaming chat responses (token-by-token) | Not present — chat is single JSON blob, and NLU is rule-based (not even calling an LLM), so there's nothing to stream even conceptually today. |
| Saved views / saved filters | Not present — no `SavedView`/`SavedSearch` model or endpoint. Filters exist only as query params re-entered each time. |

| Pagination cursor / server-side total count independent of full-set load | `GET /api/leads` computes `total` after loading and JSON-filtering the whole matching set in Python — fine at current scale, but not real server-side pagination once JSON post-filters (`no_socials`, `no_https`, `no_booking`) are used. |

| Tagging / labels on leads (beyond `category`, which is provider-derived, not user-editable) | Not present. |
| Any endpoint to re-run/refresh a *specific* company's search-source data (vs. its website analysis) | Not present — `POST /leads/{id}/analyze` only re-runs website analysis + scoring, not a re-scrape of the map listing. |

| Campaign-level analytics (open rate, click rate, per-campaign conversion) | Only global `GET /api/stats/dashboard` exists; nothing scoped to a single `Campaign`. |

## 8. Auth

**Fully open — no authentication, no sessions, no users, no tenants.**

- No `Depends()` usage anywhere resolves to an auth/user dependency — the only `Depends(...)` calls across the entire `backend/app/api/` tree are `Depends(get_db)` (a plain DB session).
- No `HTTPBearer`, `OAuth2PasswordBearer`, `APIKeyHeader`, JWT, cookie/session middleware, or any `Authorization`/`X-API-Key`-style header check exists in the codebase.
- No `User` model exists (confirmed via `backend/app/models/__init__.py` — only `Company, Analysis, StatusHistory, ChangeHistory, Campaign, Message` are registered).
- No tenant/workspace scoping field exists on any model (`Company` etc. have no `owner_id`/`tenant_id`/`workspace_id` column) — this is a **single-tenant application**: every deployment's database is one shared pool of leads visible to anyone who can reach the API.
- `settings.SECRET_KEY` exists in config (`"change-me-in-production"`) but is **unused** anywhere in the code I found (no JWT signing, no session signing) — it's vestigial/placeholder.
- CORS is configured for a specific origin allowlist (`CORS_ORIGINS`), which is the *only* access restriction in front of the API, and it is a browser-enforced control, not a server-side auth check (any non-browser client, or a request from an allowed-origin page, can call any endpoint with no credentials).

**Implication for the frontend rewrite**: there is no login flow to build against, no per-user data isolation, and no token to attach to requests. If auth is desired for the rewrite, it is 100% new backend work (no existing scaffolding to hook into) — the contract above is the complete surface as-is.
